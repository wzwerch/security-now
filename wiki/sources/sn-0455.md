# Summary

A Q&A episode. Steve reports on May 2014 Patch Tuesday (eight bulletins, two critical including one for Internet Explorer 6 to 11) and on the Certificate Authority Security Council's public statement criticizing Google for dropping live OCSP checks in Chrome, arguing that Chrome's CRLSet is merely a blacklist of high-profile certificates and that users were not told; the CAs say users would accept a small speed cost. Steve backs the point and says the Chrome revocation setting is buried in advanced options. He also covers the federal appeals court overturning the earlier Oracle v. Google ruling by holding that Java API structure can be copyrighted, which he sees as dangerous for the industry and for any compatible interface. Other items: SQRL's entropy harvester now works on all testers' Windows versions, a SpinRite story where a drive was repaired enough for DBAN to wipe it, and a shaving-product aside. Listener questions cover DANE and DNSSEC as a way to publish certificate hashes (and why adoption will be slow), whether hundreds of trusted CAs are a problem and what a misleading report about "fraudulent certificates" actually measured (local TLS-intercepting middleboxes), why disabling electronic funds transfer is a firewall-like precaution but not complete fraud protection, why certificate handling in the browser can beat OS-level handling now that XP gets no updates, how public-key trust works, and the difference between true randomness, pseudorandom generators and Intel's hardware generator.

# Key points

- May 2014 Patch Tuesday: eight bulletins, two critical (Internet Explorer all versions and one other); Steve repeats that IE should be used with caution.
- CA Security Council statement (May 8): CAs say they built OCSP and revocation infrastructure after the CA/Browser Forum revocation working group, Chrome moved away from OCSP without informing users, and CRLSet covers only a small fraction of revoked certificates; Heartbleed showed the need.
- Chrome's "check for server certificate revocation" option is off and deep in advanced settings; Steve notes it is personal when a company must revoke its own certificate.
- Oracle v. Google: Judge Alsup in 2012 had ruled APIs are like a library's structure and not copyrightable; the Federal Circuit reversed in May 2014, which Steve and Leo see as a head-shaking blow that could change how compatible interfaces are built; the patent claims had already been rejected.
- SQRL: a build with the entropy harvester ran successfully on all newsgroup testers' versions of Windows; Steve is using multiple entropy sources including the Intel hardware generator.
- SpinRite plus DBAN: a drive too damaged for DBAN to run was first repaired with SpinRite so it could be securely wiped.
- DANE/DNSSEC: a site could publish the hash of its certificate in DNS; with DNSSEC the answer cannot be spoofed, which would also address CA trust and revocation, but DNSSEC deployment is slow because servers, clients and registrars must all change.
- CAs: most certificates come from a small number of authorities, yet browsers trust hundreds; everyone wants to become a CA because it is lucrative; some security-conscious people prune their trust lists. A widely cited study claiming many fraudulent certificates reflected local interception by antivirus or corporate border appliances.
- EFT precaution (Australian listener): blocking electronic access is a useful firewall-like measure but does not protect against all fraud, and banking rules differ by country.
- PKI works because the private key never leaves the server; SQRL uses the same principle.
- A listener argues certificate handling should live in the browser rather than the OS because XP no longer receives updated untrusted-root lists; Steve agrees that is a good point.
- Randomness: one-time pads need true randomness, whereas Intel's design uses a hardware noise source to seed a pseudorandom generator inside the chip; many sources are combined for security, and entropy must not be an afterthought.
