# Summary

The title "1" refers to the number of PBKDF2 iterations that many long-time LastPass users discovered in their account settings after the previous episode. Listener Rob Woodruff wrote a small PowerShell script with a graphical interface (largely generated with ChatGPT, which Steve found startling) that decodes the obfuscated, unencrypted part of a LastPass vault (website URLs, last-touched timestamps) and flags entries encrypted in ECB mode. Steve had the script signed with GRC's code-signing certificate and hosted it. The decoded output shows that the stolen backups hand an attacker a full list of the sites each person uses plus usage timing, which is a serious privacy loss even without decryption. Since early LastPass defaults were 1 iteration (2008-2012), then 500, 5,000 and finally 100,100, and these values were never automatically raised, listeners with a count of 1 can have a typical 40-bit-entropy master password cracked in about a minute by 200 GPUs, versus about 71 days at 100,100 iterations. Steve calls this a critical product defect and says LastPass could have upgraded counts transparently at login. He explains why password length matters far more than iteration counts (each extra random character from a 95-symbol set multiplies cracking cost by 95 while iterations scale only linearly), recommends at least a million iterations and a move to memory-hard key derivation (scrypt, Argon2), and answers listener questions on migrating to Bitwarden, rotating passwords and usernames, and notes stored in vaults such as ID scans.

# Key points

- A listener-built PowerShell tool (Analyze-LastPassVault) parses the vault XML a logged-in browser retrieves, decodes URLs and flags ECB entries; Steve signed it, hosted it behind a GRC shortcut and cautioned it is only for one's own data.
- The unencrypted vault elements expose every site URL and last-used time; combined with account metadata that LastPass admitted losing (names, emails, IP addresses), attackers can prioritise high-value targets.
- ECB mode means identical passwords produce identical ciphertext, revealing reuse; CBC with a random initialization vector avoids this. Early reports show only a few ECB entries, so Steve rates it a smaller problem.
- Many listeners found their PBKDF2 iteration count at 1, 500 or 5,000, because LastPass never migrated old accounts; the count is stored in the metadata and is known to the attackers, who can sort vaults by it and attack the weakest first.
- Cracking numbers: one GPU needs about 200 years for a 50-bit password at 100,100 iterations; 200 GPUs need about one year; for a typical 40-bit password about 71 days; with a count of 1 about 61 seconds.
- Steve raised his own LastPass count to 350,000 (OWASP guidance at the time) in about five seconds; Leo set Bitwarden to two million with only a few seconds' delay.
- Entropy arithmetic: iteration count adds linear strength (350,000 vs 100,100 is about 3.5 times), one extra random character adds 95 times; 20 truly random characters give more than 128 bits, so more is unnecessary; passphrases with grammar have less entropy than random characters.
- Master password inputs are email (salt), password and iteration count, so choosing an unusual count gives no protection since attackers know it.
- Iteration counts should be enforced as a minimum and silently upgraded at login by taking intermediate key snapshots; Steve suggests at least 1,234,567 but argues PBKDF2 is aging and managers should adopt scrypt or Argon2, which GPUs cannot accelerate.
- Advice to migrating users: change passwords and, where possible, account emails; sensitive notes (IDs, passports) in vaults raise the stakes; Bitwarden has a smaller secure-note size limit.
- Listener question: no uniform API exists to rotate passwords automatically across sites.
- Steve considers potential legal liability appropriate only for demonstrable damage from reliance on LastPass's security claims.
