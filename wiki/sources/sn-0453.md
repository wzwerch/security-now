# Summary

News: FireEye found a targeted zero-day in Internet Explorer's Vector Markup Language handling (all versions IE6 to 11, exploited via Flash heap spraying); Microsoft offered a workaround to unregister VML, but IE8, the last version on XP, would not be patched, and Steve posted a blog entry with instructions and a test page. Firefox 29 shipped with a redesigned interface and encrypted Sync, Adobe issued another critical update, and the Linux Foundation announced the Core Infrastructure Initiative, funded by major companies (about 100,000 dollars a year each) to support open-source projects, with OpenSSL first, a direct result of Heartbleed. Steve then explains certificate trust and revocation from the ground up: public key infrastructure, certificate authorities binding names to keys, intermediate certificates, why revocation is needed (key compromise accounts for many revocations), certificate revocation lists and their size and caching problems, OCSP's per-certificate queries and latency, segmented CRLs, soft-fail behavior that attackers can block (Adam Langley's argument), OCSP stapling where the server supplies a fresh signed response, and the proposed OCSP Must-Staple certificate flag. Next week he will cover what browsers actually do.

# Key points

- IE VML zero-day: used in targeted attacks via a malicious Flash object; workaround unregisters the VML library; works on XP but behaved inconsistently on 64-bit Windows 7; Steve argues XP's end of support is not the issue, since this is an IE bug that also hits supported systems.
- Steve notes browsers are becoming complex operating platforms that no one can fully protect, citing Pwn2Own.
- Firefox 29's new look can be reverted with the Classic Theme Restorer add-on; security updates remain worthwhile.
- Core Infrastructure Initiative: industry sponsors (including Microsoft though not a user) fund critical open-source projects, announced weeks after Heartbleed.
- PKI basics: a server proves identity to a certificate authority, which signs a binding of name and public key; validation levels range from domain validation to Extended Validation; chains usually include intermediate certificates so the root key stays offline.
- Why revoke: stolen keys let an attacker impersonate a site until the certificate expires; studies cited say key compromise is the most common stated reason.
- CRL: a list of revoked serial numbers published at a URL named in the certificate; lists are cached (daily publication, about a week of validity), which leaves a theoretical window; lists grow as issuance grows; CAs can segment lists.
- OCSP: the browser asks a CA responder about a single certificate and gets a signed answer, usually cached; downsides are privacy, latency and failure handling. Steve's revoked.grc.com test site required pre-revoking certificates because caches were aggressive.
- Soft-fail: browsers that ignore missing revocation responses can be defeated by an attacker who blocks the check; Steve explains this is the crux of Langley's claim that revocation is broken, though protection works in some situations.
- OCSP stapling: the server fetches a signed OCSP response itself and presents it during the handshake, removing browser lookups; DigiCert offers a checker page. Weakness: an attacker with stolen keys can simply not staple, so certificates need a "Must Staple" extension, which Steve expects will be the end state.
- Short-lived certificates were floated as an alternative but conflict with pinning and other dependencies.
