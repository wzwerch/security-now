# Summary

A quiet post-Thanksgiving week. Steve discusses the Supreme Court hearing on whether iPhone users have standing to sue Apple over its App Store commission (the Illinois Brick doctrine on indirect purchasers) and argues that a curated store is a key reason iOS is safer than Android, so forced sideloading would be a security disaster. Bleeping Computer reports Google and Mozilla may remove built-in FTP support from browsers because it is rarely used and awkward to secure (the separate data channel breaks encrypted NAT/firewall snooping); alternatives include HTTPS downloads, SCP and SFTP. Steve then reacts to Google's draft Writable Files API that would let web apps persistently read and write local files after a file-picker choice, calling it a social-engineering risk despite stated safeguards. Several listener replies about last week's password discussion are answered, including a credit-card analogy for gradual SQRL adoption. The main topic is ECCploit, from the VU Amsterdam group: researchers reverse engineered the undocumented ECC schemes of AMD and Intel memory controllers and used a side channel plus composable bitflips to run reliable Rowhammer attacks even on ECC memory. Steve judges it mostly academic for end users but relevant for shared hosting and state-level actors.

# Key points

- Apple v. Pepper: question is standing under the Illinois Brick rule (only direct purchasers can sue); Apple says it acts as an agent for developers; Steve fears the consequences of forced alternative app stores.
- Browser FTP support is under consideration for removal (about 0.1% usage); FTP's dual-connection design complicates NAT/firewalls and TLS; alternatives named include SCP, SFTP, FISH and plain HTTPS.
- Writable Files API proposal: persistent, picker-based file access for web apps; risks include modifying executables and ransomware-like encryption; proposed mitigations include restricting directories and file types and re-prompting.
- Listener replies: SQRL is zero-friction after initial setup; sites can delegate authentication to a shared identity domain; the spec deliberately stays minimal and does not transmit profile data.
- Rowhammer recap: repeated DRAM row reads cause bitflips in neighbouring rows; parity detects single flips, ECC corrects single and detects double flips.
- ECCploit: reverse engineering of one AMD and three Intel ECC functions with a hardware probe, Rowhammer and cold-boot; a memory-controller timing side channel reveals correction events; reliable attacks possible on ECC systems.
- Some low-power systems reduce DRAM refresh and rely on ECC to compensate, which Steve criticizes.
- Impact assessment: dangerous mainly in shared hosting and targeted attacks; browsers were already hardened against Rowhammer.
