# Summary

Steve closes his certificate revocation mini-series after spending three weeks researching it and building test pages (including a revoked-certificate site). News: Microsoft reversed course and shipped an out-of-cycle Internet Explorer fix that also covered Windows XP, a rare exception after support ended; the "Covert Redirect" OAuth/OpenID issue, which Steve calls a rediscovery of a known problem that sites avoid by registering exact redirect URLs; Andreas Kurtz's finding that email attachments on iOS 7.1 devices (an iPhone 4 in his tests) were not protected by the data-protection encryption Apple claimed, which Apple promised to fix; and the US government's NSTIC internet identity pilot, which Steve views with caution after the NSA revelations. The main topic explains why revocation is genuinely hard: legacy and overloaded certificate fields, searching chains in reverse, multiple possible paths, purpose and path-length constraints, and per-library support, so browsers and operating systems behave differently. Chrome relies only on a small curated CRLSet (about one percent of certificates, from 53 authorities) and ignored most of the roughly 140,000 certificates revoked after Heartbleed, Firefox can enforce strict "must check" revocation, Windows and Safari check by default but Safari's settings are weak, Android lacks the APIs and iOS checks only EV certificates. He also discusses DNS-based alternatives (CAA and TLSA records with DNSSEC, known as DANE) and argues revocation matters even if an attacker can sometimes block it, disagreeing with Adam Langley and Larry Seltzer's column that praised Google's approach. SQRL work resumes full time.

# Key points

- Microsoft shipped an out-of-cycle IE security update for the VML zero-day, including Windows XP, requiring a reboot because of IE and Explorer entanglement; Steve says they did the right thing.
- Covert Redirect (OAuth/OpenID): an attacker site can redirect authentication tokens when providers allow open redirect URLs; the spec already advised strict redirect registration; Steve thinks the media overhyped it.
- iOS 7.1 attachment protection: Kurtz showed IMAP mail attachments were stored unencrypted on certain devices despite Apple's design; Apple said it would fix it. Steve guesses a conditional-code mistake across multiple security architectures; Rene Ritchie quoted Steve's earlier praise.
- NSTIC (National Strategy for Trusted Identities in Cyberspace): the US government begins pilot internet IDs; Steve sees potential value for tax filing but terrible timing and unknown technology.
- Why revocation is hard: certificate standards evolved with overloaded fields and backward compatibility; chain building requires searching issuers, may find multiple paths, and must apply purposes, name constraints and path-length limits; each link must be checked for revocation.
- Chrome: uses only CRLSet, a size-limited list that covers about 1 percent of revoked certificates; Steve's page showed it lists certificates from 53 authorities, and none of the Heartbleed-revoked ones in bulk; Google's stance is that fail-soft revocation is not worth slowing users.
- Firefox: checks OCSP by default, supports hard-fail "must check", and is building a new libpkix-based library; strict mode defeats Langley's soft-fail argument at a cost of some failures behind captive portals.
- IE/Windows: revocation on by default since IE7 and in the Windows crypto API; Safari/OS X has settings but they are hidden or race-prone; Android's Java layer lacks revocation support so only Firefox checks; iOS checks EV certificates only.
- DNS-based options: CAA records tell which CAs may issue for a domain; TLSA/DANE ties a server's key to its DNS record but needs DNSSEC, which is deploying slowly.
- OCSP Must-Staple: Steve will advocate it; he cites data that key compromise is the leading cause of revocation, disputing a claim in a column that said otherwise.
- Revocation matters because attackers cannot always block lookups (for example when they control only the path to the website), and ignoring it leaves users with no protection after a key theft such as Heartbleed.

# Other segments

- SQRL: Steve is back full-time on coding after the revocation detour, with high-quality entropy gathering done.
- SpinRite: a MacBook Pro made fast again by SpinRite Level 4 after reimaging failed; Steve explains modern drives rely on constant ECC so weak sectors slow reads long before failing.
